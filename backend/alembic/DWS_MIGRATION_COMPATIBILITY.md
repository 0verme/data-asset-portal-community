## Ledger and authoring rules

1. The ledger must contain exactly one known Alembic revision on the repository's single head. Unknown, empty (except the narrowly verified DWS `apply` recovery below), or multi-row values fail closed; they are never guessed as fresh.
2. Fresh DWS executes the complete canonical `dws.sql`, verifies its schema, and then advances through the revision runner to the *dynamically discovered repository head*. Structural revisions are adopted from the verified baseline; additive seed revisions (`0009` and `0012`) still execute because the schema baseline does not represent their rows. It does not replay changes already represented by that baseline.
3. Existing DWS executes every missing revision in order. A revision value is persisted only after that revision's post-condition is confirmed. A failed or partially applied revision is never stamped complete.
4. DWS may use a JDBC-specific dialect/runner and per-revision adapter. Each adapter must declare the physical schema, DWS syntax/constraint/distribution policy, retry/partial-state checks, and tests; do not silently skip a revision or maintain the fresh baseline alone. A test asserts that every Alembic revision except `0001_baseline` has a registered DWS adapter.
5. DDL rollback guarantees for DWS 8.1.3 are unverified. Until live validation establishes otherwise, assume DDL may survive rollback: make steps idempotent only when safe, detect partial state, retain the previous ledger, report the revision/error and require explicit repair for conflicts.
6. Revision ledger stamps use a single-row `UPDATE` (or first-row `INSERT`) and read back the resulting value; they do not delete the last known-good row before replacement. If a revision's physical postcondition is verified but ledger update/commit fails, stop before the next revision. A retry re-inspects the schema and adopts the revision if its postcondition is present; it never blindly replays DDL/DML. If the commit acknowledgement is uncertain, the runner proceeds only if a post-rollback read confirms the target revision; otherwise it fails closed.
7. An empty DWS ledger may be recovered by `apply` only when the full current canonical physical schema verifies. This covers a fresh baseline whose DDL committed but initial ledger insert failed. Partial schema, multiple ledger rows and unknown revision strings remain blocked. Other dialects keep their explicit existing-database baseline/stamp flow.
8. Downgrades remain unsupported. Tests use isolated disposable SQLite databases, recording JDBC connections or clearly identified disposable integration schemas. The Agent must not connect to or alter a maintainer production database.

## `status` / `plan` / `apply` / `verify` contract and fault recovery

- `status` is read-only and reports the recorded revision plus the dynamically discovered repository head. Unknown or malformed ledgers fail before any write.
- `plan` is read-only; it inspects each missing revision in order. Once a predecessor is pending, later states that cannot yet be proven are shown as `pending`, not treated as conflicts or as safe to skip.
- `apply` validates the revision path before any stamp, executes only the missing ordered steps, re-reflects each physical postcondition, and stamps that revision before starting the next. Head apply is a no-op for revision DDL/DML, then checks the complete head contract. Revision seeds are keyed by stable natural codes and only missing values are inserted.
- Online DWS `verify` requires the ledger to equal the repository's current head, the canonical physical schema to match, and every registered revision adapter's post-condition to be `APPLIED`. This catches data-only seed drift and constraints not represented by the generic schema parser. A schema that looks current but still records `0005` (or any earlier revision) is not accepted as verified.
- Stamps preserve the existing ledger row using one conditional `UPDATE`; the old row is never deleted before its replacement. The runner reads back the stamp before continuing. A write/commit failure stops immediately: if the old ledger is intact, retry re-inspects the revision and adopts a completed physical postcondition; if the ledger reads as the target after rollback, that exact value is accepted; any empty/unknown/multi-row state fails closed.
- If the initial fresh DWS baseline is physically complete but its first ledger insert failed, `apply` may recover by verifying the complete canonical baseline and stamping `0001_baseline` before replaying the inspection/adoption path. It does not recover a partial baseline or silently stamp an unknown schema. The empty-ledger recovery path is DWS-only.
- DWS 8.1.3 DDL transaction/autocommit, savepoint and rollback semantics have not been measured. Tests model persisted DDL on failure and validate the inspection-based recovery policy; they are not evidence of live server behavior.

## Legacy `0001_baseline` ambiguity audit

### Why `revision = 0001_baseline` is ambiguous

GaussDB/DWS fresh installs always executed the *current* canonical `dws.sql` and stamped only `0001_baseline`. Because `dws.sql` kept absorbing new feature structures, two instances with the same ledger value can have different physical schemas:

```text
instance A: revision=0001_baseline, physical schema ~ early baseline
instance B: revision=0001_baseline, physical schema ~ complete current baseline
```

Git history confirms the released baselines form a *prefix* of the revision chain: each structural revision's `dws.sql` change landed in the same commit that introduced the revision.

| Baseline commit | Release | Baseline change |
|---|---|---|
| `43d6548` | baseline | 24 tables; no RBAC/open-module tables; `p_asset_table.table_name` unique; no indicator semantic columns |
| `7a438a4` | #118 | + `0003` open repository module tables |
| `47f4bf6` | #119 | + `0004` metadata ingestion identity columns/unique |
| `9ac81d4` | #123 | + `0005` RBAC tables |
| `f090887` | #196 | + `0006` field mapping upstream identity |
| `a76521f` | #200 | + `0007` binary status contract |
| `71a8921` | #210 | + `0008` indicator semantic columns/index |
| `2ee912f` | #235 | `0009` is data-only; **no** baseline change; current released semantics were narrowed by #488 to platform-only `UPSTREAM_DB_TYPE` values, with retail Demo rows owned by explicit Demo seed |
| `d37c8b4` | #301 | + `0010` field mapping identity index |
| this Issue | #313 | + `0002` portable filter index in every canonical baseline |
| `973c709` | #317 | + `0011` `p_push_job.freq_desc` widened to `VARCHAR(1000)` in every canonical baseline |
| this Issue | #321 | + `0012` search recommendation table and minimal neutral defaults in every canonical baseline |

Consequences:

* `revision == 0001_baseline` never means "replay `0002`..`0010`"; it means "inspect the physical schema and adopt every revision whose post-condition already holds".
* `0002` is missing from every released baseline, so even a nearly-head legacy instance still needs that one index.
* `0009` is a data-only revision that no schema baseline can represent, so fresh installs and existing upgrades execute its additive platform `UPSTREAM_DB_TYPE` seed; current main's #488 contract excludes retail `UPSTREAM_DEPT` Demo values, which remain the responsibility of an explicit Community Demo seed.
* `0012` represents both a new table and its defaults: canonical current baselines already contain the table, but the adapter still inserts only missing defaults; older instances create the table from canonical DWS DDL before seeding.

### Resolution contract

The runner combines the ledger with physical post-condition inspection:

```text
ledger revision
  + schema post-condition inspection
  -> per-revision action
```

Every adapter returns exactly one of three states:

| State | Meaning | Runner action |
|---|---|---|
| `APPLIED` | the complete post-condition already exists | adopt; normalize the ledger only |
| `NOT_APPLIED` | the revision did not run, or only its documented, provably idempotent and non-destructive completion is missing | execute the adapter |
| `CONFLICT` | the observed state is neither the pre-condition nor the post-condition | fail closed; never guess, delete or rebuild |

After `NOT_APPLIED` execution the adapter is inspected again; the ledger advances only after the post-condition is confirmed. If a revision fails, the ledger stays at the last fully confirmed revision and the next run re-inspects the physical state.

### DWS-specific constraints encoded by the adapters

* **No physical foreign keys.** DWS does not support them; `0006` records the upstream relation as a logical `upstream_system_id` column + unique index only, matching the canonical `dws.sql` policy from #303.
* **No `CREATE INDEX IF NOT EXISTS`.** The adapters inspect the index first and then emit plain `CREATE INDEX` (GaussDB 8.1.3 rejects `IF NOT EXISTS`, see #304).
* **Distribution clauses are preserved** by creating missing `0003`/`0005` tables from the canonical baseline statements instead of duplicating historical DDL.
* **`0009` seeds only missing platform `UPSTREAM_DB_TYPE` codes**; it never inserts retail Demo department rows and never overwrites/deletes existing customized or historical codes. The explicit Demo seed owns the complete retail department sample.
* **`0012` creates from canonical DWS DDL and seeds only missing `(keyword, category)` rows**; existing keywords, enabled state, sort order, IDs, and custom rows are never overwritten.
* **`0013` adds only a non-unique field lookup index**; existing mapping rows are untouched, and an unexpected same-name index is rejected rather than replaced.
* **Check-constraint detection for `0007` and `0012`** uses `pg_constraint` + `pg_get_constraintdef`; both target-table queries are part of the maintainer's real-DWS validation checklist.
* **DDL transactionality is assumed unsafe.** The runner commits each revision only after its post-condition is confirmed; if DWS auto-commits DDL, an interrupted revision is re-inspected and either safely resumed or reported as a conflict.
