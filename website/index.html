01 / 为什么需要 DAP

这几件事，做过数仓的人都经历过。

当元数据散落在个人文档和口头交接里，每一次找表和对齐口径都在重复消耗团队精力。

  1. 01
    新人上手慢。

    一张表能不能用、更新频率是什么，要先找到写表的人问一圈。

  2. 02
    同一指标两份口径。

    两张报表的「下单用户数」对不上，没人说得清哪份才是权威定义。

  3. 03
    人一走，知识就断层。

    核心字段的业务含义、枚举码值和加工背景，留在离职同事的脑子里。

  4. 04
    业务问数缺少可信底座。

    没有经过校验的资产与口径出处，同一个问题换个人或换个模型查，口径就变了。

理念 / DAP 的由来

数据可以入仓，但
责任、语义和经验不会自动入仓。

DAP 不是从竞品分析里来的。它来自一段真实的数仓经历：180 多个上游系统、3800 多张表入仓，向下支撑 100 多个业务系统。做到这个规模后发现，SQL 反而是最省心的部分——真正耗人的，全在 SQL 之外。表总能建，数据总能接。难的是几年以后，系统换了、人也换了，还能不能回答清楚：这份数据为什么在这里，这个口径为什么这么定，谁在用，谁负责，上游变了会影响谁。

01

让责任入仓

数据出了问题，最难的往往不是修，是说不清该谁负责：谁认业务定义、谁保障生产、谁在使用、出了争议谁拍板。DAP 把负责人、使用关系和影响范围跟着资产一起沉淀，而不是等出事了再拉群找人。

对应：负责人维护 · 血缘与影响分析 · 操作审计

02

让语义入仓

口径很少是开发前就定好的，多数是在开发、测试、上线后对数的过程中慢慢“长”出来的。如果不趁那一刻记下来，它就只活在当事人的记忆里。DAP 让口径定义、字段释义、码值含义直接挂在资产上，并给出处。

对应：指标口径 · 字段释义 · 标准词根与码值 · 证据链

03

让经验入仓

最难交接的不是怎么做，是为什么这么做、为什么那段“多余”的逻辑没人敢删、为什么这个任务失败了不能直接重跑。这些判断来自事故和历史，不写下来，人一走就归零。DAP 要做的，是让经验依附于资产留存，而不是依附于某个人。

对应：业务说明 · 加工背景 · 血缘快照

血缘在 DAP 里不是一张好看的展示图，它是生产风险控制：上游要改一个字段时，你至少得知道应该去敲哪些人的门。

ETL 能把数据自动送进仓库。 但责任、语义和经验，只能靠人有意识地留下来。DAP，就是为后面这三样做的。

02 / 检索与问资产

问资产，
不是盲目问数。

DAP 默认提供确定性关键词检索；开启可选 AI 问答后，也绝不直接编造业务数字，而是用可追溯的证据链锁定哪张表、哪个字段、口径写在哪、数据从哪来，并把校验后的资产结构交给上层应用。

  • 全链路透明：清晰呈现检索词拆解、检索轮次、命中资产与目录证据来源。
  • 目录权威校验：所有返回的候选资产均按当前目录稳定 ID 回查核验，拒绝自由文本幻觉。
  • 按需渐进启用：确定性搜索零外部依赖开箱即用；RAG 推荐与单轮 AI 问答默认关闭、可独立插拔。

证据链追踪样本

一次「问资产」从问题拆解到目录回查的完整链路

零售演示数据

    近 30 天下单用户数的口径是什么、从哪张表出？

    提取的关键检索词

    R1exact“下单用户数” → 命中 1 项指标定义

    R2keyword“下单 用户 30天” → 命中 3 项汇总表与字段

    R3hybrid“下单用户 去重 口径” → 命中 1 条语义关联证据

  3. 3 / 目录权威校验命中
    指标资产
    order_user_cnt_30d
    出数主题表
    dws.trade_user_stat_d
    结果字段
    dws.trade_user_stat_d.order_user_cnt
  4. 4 / 溯源证据锚点
    指标口径定义
    order_user_cnt_30d
    物理字段注释
    order_user_cnt
    已导入血缘快照
    dwd.trade_order_d → dws.trade_user_stat_d

所有候选资产均由 DAP 按当前目录稳定主键（assetId / fieldId）回查重建。上方表名与指标来自仓库内置零售演示数据集。

  ],

    { "type": "table",  "id": "dws.trade_user_stat_d" },
    { "type": "field",  "id": "dws.trade_user_stat_d.order_user_cnt" }
  ],
  "evidence": [
    { "asset": "order_user_cnt_30d", "source": "metric_definition",
      "text": "近30天内成功下单的去重用户数" },
    { "asset": "dws.trade_user_stat_d.order_user_cnt", "source": "field_comment" },
    { "asset": "dws.trade_user_stat_d", "source": "lineage_snapshot",
      "path": "dwd.trade_order_d -> dws.trade_user_stat_d" }
  ]
}

上层应用拿到的，不是一句模糊回答

而是一组带权威出处的结构化资产引用：每一项都能精确定位到指标口径、字段注释或血缘快照。上层应用既可据此安全拼接查询，也可在证据不足时明确拒答。

核心检索与问答端点：GET /api/search · POST /api/ai/ask/stream

03 / 资产就绪度

用着用着，
就把资产补全了。

不需要搞运动式的治理专项。每个模块里有多少资产说得清楚、口径有出处，直接用就绪度百分比直观呈现——不绑架审批流，用最小的认知成本告诉团队哪里还缺。

各模块资产就绪度

基于完备性规则实时计算的目录健康度概览

零售演示数据
  • 表资产82%

    计入标准：已维护负责人与表业务说明

  • 字段含义64%

    计入标准：已填写字段中文业务释义

  • 指标口径71%

    计入标准：已维护口径定义文本并绑定出数表与字段

  • 标准码值90%

    计入标准：已维护码值枚举明细与业务说明

  • 报表与 API55%

    计入标准：已建立与底层表或指标的来源关联 优先补齐

  • 血缘快照38%

    计入标准：已导入激活态上下游血缘快照的表占比 优先补齐

就绪度 = 满足完备性规则的资产数 ÷ 该模块资产总数；低于 60% 自动标记「优先补齐」，引导日常高频维护。

04 / 架构取舍与边界

专注资产目录，
把重型链路留在外部。

DAP 之所以能在 2GB 内存的内网单机上轻松跑起来，是因为我们只聚焦「数仓资产目录」这一件事，主动对以下四类重型能力做减法：

边界 01

不内置数据采集与任务调度

不侵入企业既有的 ETL 编排或文件推送执行。由外部系统整理好元数据后，通过版本化 Metadata Contract 标准导入。

边界 02

不主动连接或扫描生产库

DAP 不持有业务生产库凭据，不主动探查库表，也不在运行时解析复杂业务 SQL，从根源上降低内网安全合规顾虑。

边界 03

不内置重型血缘计算引擎

专注于流畅浏览与检索已导入的血缘快照（支持最多 30,000 节点 / 75,000 边的快照替换），把方言解析交给上游采集器。

边界 04

不绑架质量检测与审批流

不内置重型数据 Profiling 与工单审批流转。资产就绪度只做轻量透明的健康提示，让数据团队保持敏捷。

如果你需要覆盖数百个连接器与全套治理工作流，OpenMetadata 或 DataHub 会是更合适的选择。 DAP 选择用更少的组件与更低的运维成本，为数仓团队交付一个开箱即用的轻量目录。

06 / 开放接入契约

采集在外面，
DAP 只管幂等接收与权威展示。

无论你用的是自研 Python 脚本、Airflow 调度还是现有治理平台，只需按版本化 JSON Contract 提交 HTTP 请求，即可把元数据持续同步进 DAP。
